Getting started

Homelab Monitor watches the things on your network: whether they answer, how fast, what they report over SNMP and whether a port or web page responds. It keeps history, raises problems, tells you on Telegram and can run commands on your hosts when something needs doing.

Installing

  1. Open a shell on the Proxmox host (in its web interface: your server's name under Datacenter, then Shell), then download the installer and check that it is the real one. Copy this whole block and paste it: 
    U=https://github.com/The-Flying-Pancake/Home_Monitor/releases/latest/download
curl -fsSLO $U/home_monitor.sh
curl -fsSLO $U/home_monitor.sh.sig
echo 'release@home-monitor namespaces="home-monitor-release" ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIKQPTSJq7103aQVXEseRIWBM/Rtm/z8tiJyBboEcd0lz' > release-signers
ssh-keygen -Y verify -f release-signers -I release@home-monitor -n home-monitor-release -s home_monitor.sh.sig < home_monitor.sh
    You should see a line starting with Good "home-monitor-release" signature. If you see anything else, do not run the file: download it again, and if it still fails, report it on the project's GitHub page. Check the file before you change anything in it, because an edited copy no longer matches its signature. This proves the file is the one the project signed, so a changed download or a swapped release file is caught. It does not protect against someone taking over the project's GitHub account, who could change the key shown here too. The release key's fingerprint is SHA256:VfgS3MkxWYcs7WXOVRScDX29tjA3pWXCf5d4VwDByQQ: keep it somewhere of your own to compare. Then make it runnable and start it: 
    chmod +x home_monitor.sh
./home_monitor.sh
    chmod +x marks the file as a program you may run; once is enough. Copied it over from Windows instead? Run it as bash home_monitor.sh so it can repair the Windows line endings itself. The settings block at the top of the file (storage, network, backups and more) can be changed first with nano home_monitor.sh, but most installs never need it. Before 0.10.0 the file was called infra.sh: it is the same installer.
  2. Without options it shows a menu: install, upgrade, check, restore, rebuild or preview. Type the number, then yes to go ahead. Options such as --upgrade skip the menu. A first install asks in a framed box for the container ID (a free one is offered), its name, its address (dhcp or a fixed one such as 192.168.1.51/24 with its gateway) and whether to start with demo data. It then asks for the kind of container. If the container will be privileged, or root can log in over SSH with a password, it says so plainly, offers to take a public key and asks you to type ACCEPT. Upgrades show the same warnings without asking. Enter keeps the answer shown, which comes from the settings block. The container gets a 20 GB disk. It then creates the container, installs everything and prints the address and a setup code. Run without a person at the terminal (or with HM_NO_ASK=1) it asks nothing and uses the settings block. The new container gets the Proxmox tag homelab-monitor and a note saying so: that tag is how upgrades find it.
  3. Open the address in a browser, create your account (the setup code proves you are the one who installed it) and follow the setup guide.

On a phone: the menu sits behind the menu button at the top left; tap beside it to close it. Tables too wide for the screen scroll sideways inside their panel; windows fill the screen. The Devices list shows status, name, address and ping; tap a device for the rest. Arranging dashboards, the map and workflows is easier on a larger screen.

In a VM or without Proxmox: download home_monitor.sh to the machine and check it with the same block (Ubuntu 22.04 or newer, Debian 12 or newer; best a VM of its own; sudo apt install -y curl openssh-client if they are missing), chmod +x home_monitor.sh and run sudo ./home_monitor.sh --local. It asks about demo data too. It skips the container steps and installs everything on that machine. The outbound firewall then covers the whole machine (package sources and Telegram only), so set NTP_SERVER at the top to a time server on your network (your router, say) unless the machine already uses one. Your logins and SSH settings are left alone. No firewall is added for incoming traffic: the web port and UDP 161 (SNMP) can be reached by anything that can reach the machine. Upgrade later with sudo bash home_monitor.sh --local --upgrade; --rebuild does not apply.

Demo data: answer yes to Start with demo data (or run ./home_monitor.sh --demo, or set DEMO="yes" at the top) and the new monitor fills itself with sixteen made-up devices and a week of history, to look around before pointing it at your network. They use addresses set aside for examples (192.0.2.x, 198.51.100.x and 203.0.113.x); their readings are invented on the monitor, so nothing is sent to them. Devices you add yourself are checked for real. Settings, Demo data (shown only while there is demo data) removes them: the demo devices with their history and events, and the groups and tags that came with them. Your account, settings and your own devices stay, and with nothing left the setup guide opens to find your network. A restore (RESTORE="latest") never adds demo data.

Lost the setup code before creating the account? On the container (or the --local machine), /root/setup-code.sh makes a new one. It refuses once an account exists.

The setup guide

It runs once, on a fresh install. The rest of the app stays locked until it is applied. Every step can be skipped and changed later in Settings.

  • Network scan: pings every address in your subnets and asks each one over SNMP what it is.
  • Devices: tick what to monitor. Each device can be Ping only or use an SNMP template.
  • Services: looks for open ports (web pages, SSH, file shares, media servers) on the devices you ticked; each port you tick becomes a port check.
  • Monitoring: how often things are checked and how long history is kept.
  • SSH, Syncthing, NFS, Telegram: optional extras. Telegram has its own topic below; Syncthing and NFS are about backups; SSH credentials are under Automation.
  • Review: what will happen, in plain words; your password confirms it.

Finding your way around

  • The menu on the left lists the pages. Proxmox, Wi-Fi (from UniFi) and Pi-hole appear once they are connected in Settings. Inventory is hidden from users limited to some devices.
  • Settings has a menu of its own: it slides in when you open Settings. Back slides the main menu in again and returns you to where you were.
  • After an upgrade, your next login shows what changed. What's changed on this Guide page shows the whole list again.

Version numbers

Settings, System shows the version the monitor runs (for example 0.4.0). The installer and every backup record it too. The middle number goes up for new features or a change to the database; an upgrade then brings your data up to date. The last number goes up for fixes and small changes to what is already there.

One address

Fill in the address and press Test before adding: Test ping, Test & auto-detect (which also picks the SNMP template) or Test connection. Something that is off right now can still be added: tick Add it even if it does not answer yet.

Scanning the network

  • Ping or SNMP: every address in the subnets is pinged and asked over SNMP what it is. For each host found, Monitor as offers Ping only or an SNMP template; hosts without SNMP start as Ping only.
  • Service: looks for open TCP ports. Common services tries about 80 well-known ports and takes seconds; Choose ports takes lists and ranges such as 22,80,8000-8100; All 65,535 ports tries every port.

A full scan takes a while: about a minute per host on a quiet network, longer for hosts with a firewall. It first finds which hosts are up, then scans only those. Open ports appear as they are found. The bar shows how far it is and roughly how long is left. Stop keeps everything found so far.

Scans only accept private ranges (10.x, 172.16 to 31.x, 192.168.x), up to 1024 addresses at a time.

The Devices page

Every device, grouped (see Groups and tags), with status, response time, CPU, memory, ports and when it was last seen. The tiles at the top filter the list: online, offline, with problems, wireless clients.

  • Group and tag filters above the list show one group or one tag. Untick Group them for one flat list.
  • + tag beside each name opens the tag manager for that device. When it has tags, a small bubble shows how many; hover over it to see them. See Groups and tags.
  • Tick boxes next to the names select devices: then Add tags, Remove tags or Delete selected act on all of them.
  • Poll checks one device now; Poll all every device.
  • Current problems above the list shows what is wrong now and needs someone. Acknowledge (with an optional note) marks one as seen to: it stops reminders and moves to Acknowledged problems just below, where it stays until its cause clears. Unacknowledge brings it back. A Device restarted notice leaves the list after a minute.
  • A small mark next to a status shows the device's worst open problem (!) or something that happened in the last half hour, such as a restart (i). Hover over it for what; click it for the device's events.

A device's page

Click a device's name. Tabs appear only when the device has data for them: Overview, Ports, Neighbours, Wireless, Storage, Health, Processes, Software, Graphs, DNS, Custom values, Latest Data and Events.

The buttons at the top: Poll now checks it at once, LIVE turns live mode on or off, Host actions and Fix SNMP appear for Linux hosts, Maintenance keeps its messages quiet for a while (see Maintenance windows), Alert rules opens this device's own rules, then Edit device and Delete. Its open problems are listed under the title; Device restarted stays there for the first hour after a restart.

  • Overview: the headline figures, availability (see Availability), system details, recent events and a few graphs. Choose graphs picks which graphs (up to 12) and their order is kept; Use the default goes back to the usual set. Everyone sees the same Overview for a device.
  • Graphs: pick the range at the top. Drag across a graph to zoom in, Reset zoom to go back, Enlarge for a big view with its own range and a comparison with the previous period. Hover for the exact readings. Add to overview on a graph puts it on the Overview (On overview takes it off again). On a graph with more than one line (download and upload, for example) click a name under it to hide or show that line; the scale and the readout follow. The enlarged view starts with the same choice. A busy graph is drawn as a smooth average with a faint band up to the highest reading, so spikes stay visible.
  • Live: while a device page is open its figures refresh every few seconds; nothing extra is stored.
  • Custom values: SNMP values the device's template does not read (on any device polled over SNMP). Browse lists what the device answers, starting with its vendor's own values; Use on a row (or + Add by OID) makes it a value that is polled for this device or every device on its template. Each number gets a graph here and on the Graphs tab, can go on the Overview, can open a problem when it crosses a threshold and can start a workflow (Automation, A measurement goes above or below a value, where it is listed by the name you gave it).
  • Latest Data: every value as last read.

Edit device

The window has two columns:

  • The device: its name; for a service the check (TCP port or web page) and the address or port; its group; its tags, shown as coloured labels, with Change tags to open the tag manager.
  • How it is watched: the template and how often it is pinged. For a device read over SNMP, a box holds the community, the port and how often it is read. SSH for host actions and workflows is not set here: it uses a stored credential (Automation, Credentials).

Below them, Place on the map and details holds the device it is connected to (its uplink, for the map), the port on that uplink and corrected details (location, model) that replace what the device reports.

Fix SNMP (Linux hosts)

Many Linux hosts only show basic system information over SNMP. Fix SNMP logs in over SSH, shows you the new /etc/snmp/snmpd.conf before anything is written, keeps a dated backup, restarts snmpd and checks from the monitor that interfaces, CPU, memory and storage now answer. If they do not, the backup is put back. It needs a stored credential (root or a user with passwordless sudo) and the host's SSH key approved; Copy as commands gives the same steps to paste by hand.

When the SSH login itself fails (refused, no answer or nothing listening), Copy console commands appears beside Preview changes. It copies one line to paste into the host's root shell (on Proxmox: the guest's Console). That line installs SSH if it is missing, lets the monitor's address log in, checks the new SSH settings before using them and restarts SSH. With an SSH key credential it adds the key for the monitor's address only and turns password logins from the monitor off; root may then log in by key only. With a password credential (or none) it turns on password login from the monitor's address, root included, and asks you first. It sets no password: if the account has none yet, it tells you to run passwd. Then approve the host key if asked and press Preview changes again. Host actions offer the same button after a failed login.

The new file allows only this monitor's address (and the host itself). Run it from the monitor that will poll the host.

Groups and tags

Groups decide where a device is listed. Every device is in exactly one: by default the one its template suggests (a switch template puts a device in Switches) or the one chosen under Group in Edit device.

Tags are labels for whatever cuts across groups: a room, an owner, how critical something is. A device can have up to 20.

The tag manager

On the Devices page, + tag beside a device's name shows a bubble with the number of tags it has; hover over it to see them. Click it to open the tag manager:

  • Applied: the tags on the device. Click one to take it off.
  • Available: the other tags. Click one to add it.
  • The box below makes a new tag: type it and press Add. New tags join the list in Settings, Groups and tags, where they get a colour and a description. Manage tags goes there.

Press Save tags to keep the changes. The same window opens from Change tags in Edit device; there the tags are saved with the device when you press Save changes. To tag several devices at once, tick them and press Add tags or Remove tags: put the tags under Applied and confirm. Remove tags offers only the tags those devices have.

Settings, Groups and tags

  • Add groups of your own, rename any group (built-in ones too) and put them in the order you want lists to use. Deleting one of your groups sends its devices back to the group their template suggests.
  • Give each tag a colour and a description. Put tags in the order you want. Renaming a tag renames it on every device and in its alert rules; deleting it removes it from both.

Where they are used

  • Filters on the Devices, Availability and Events pages.
  • Dashboard tiles: adding a tile that can be narrowed asks which devices it covers (all of them, a group or a tag); the list in the tile's header changes it later while you edit the dashboard.
  • Alert rules: every tag can have its own rules (see Alerts and problems).
  • Maintenance windows for a group or a tag. Your own Telegram commands can also cover the devices of a group or a tag.

The dashboard

The first page: tiles for status, problems, availability, the internet connection, busy ports, wireless, device load and recent events, plus graph tiles for any device graph you choose. Click a tile's figures to open the data behind them.

Active problems lists what is wrong now and has not been acknowledged; once you acknowledge one it leaves the dashboard and waits under Acknowledged problems on the Devices page. A Device restarted notice (info) leaves it after a minute; warnings and worse stay until they are fixed. The restart stays on the device's own page for the first hour.

Several dashboards

  • + Add dashboard beside the title opens a window: give the dashboard a name, then pick Blank or one of 20 ready-made dashboards. Each card lists the tiles it brings.
  • The ready-made ones: Overview, Problems first, Wall screen, Morning check, Outage, Minimal, Network, Internet, Wi-Fi, Proxmox, Servers, Storage and NAS, DNS and Pi-hole, Automation, Maintenance, New and unknown devices, Capacity, Websites and services, Homelab at a glance and Power and printers.
  • Once there are two or more, a list beside the title switches between them. Your browser remembers the one you looked at last and opens it next time.
  • Dashboards are shared: every user sees the same ones. A change is saved for everyone.

Changing a dashboard

Press Edit dashboard. While editing, the bar at the top has:

  • The grid width (2 to 12 columns) and + Add tile.
  • Rename for the dashboard's name.
  • Reset to default, which puts back the standard Overview tiles.
  • Delete, shown only when there are two or more dashboards. The others stay.

Each tile then shows its own tools: Rename gives it a title of your own (leave it empty for the standard name), the arrows move it earlier or later, − and + make it narrower or wider and × removes it. You can also drag a tile by its header to move it and by its bottom-right corner to resize it. Graph tiles have Configure (device, graph, range, comparison). Press Done to finish.

Tiles

  • Status summary, Active problems, Device availability, Internet (WAN), Busiest ports, Wireless, Device load, Recent events and Graph.
  • Offline now: the devices that do not answer.
  • Proxmox guests, Pi-hole and Disks filling up: figures from Proxmox, Pi-hole and the storage forecasts.
  • Host actions and Workflow runs: what ran lately.
  • Maintenance windows and New devices (from the Inventory).
  • Note: plain text of your own, such as who to call or where the spare cables are. Edit text on the tile writes it.

Status summary, Active problems, Device availability, Recent events, Busiest ports, Device load, Wireless and Offline now can be narrowed to one group or one tag. Adding one asks which devices it covers; the list in its header changes that later.

Availability

Like a status page: every device with its uptime and response time. Choose 24 h, 7 d, 30 d or 90 d at the top; the bars, the uptime figure and the average follow it (hourly bars for a day, quarter days for a week, days beyond that). Grey means nothing was checked then, for example while the monitor was stopped, so it counts neither as up nor down.

Each device's Overview has the same card, with the four uptime figures as buttons, the last checks and the list of down periods in the chosen range.

Alerts and problems

A problem opens when a condition holds: a device stops answering, CPU stays above a threshold, a disk fills up, a service stops answering. It shows on the Devices page, the dashboard and the device. It closes itself when the condition clears.

Alert rules (Settings, Alert rules)

Each rule has: on or off, a threshold where it has one, a wait (how many minutes the condition must last before a problem opens) and a severity. It also says whether it goes to Telegram, whether a resolved message follows and whether the phone rings.

Severities are info, warning, high and critical. Info problems are notices: Device restarted is one. It leaves Active problems after a minute. Warnings and worse stay until the condition clears. A problem that comes from a threshold must stay clear for a few minutes before it closes (Resolve after, 5 minutes by default), so it does not flap.

Apply to chooses where you set them. Each level overrides the ones before it:

  1. All devices: the defaults for everything.
  2. One template: every device using it.
  3. One tag: every device with that tag, whatever its template. When two tags of a device set the same thing, the tag lower in the list (Settings, Groups and tags) wins.
  4. One device: that device only. Always the last word.

Faded values are inherited (hover to see from where); outlined values are set at the level you are looking at. Overview lists everything set anywhere in one place.

Example: tag your NAS boxes storage, then set the disk full threshold to 85% for the tag. A NAS that needs something different still gets its own value on its device level.

One alert for one failure

When a switch goes down, everything behind it on the map stops answering too. You get one message, for the device that failed, listing the devices behind it; theirs say "unreachable behind switch-01, which is down" and send nothing of their own (nor a "back online" message when it returns). If the map has a link wrong, set the uplink in Edit device, Place on the map and details.

Warnings before things break

  • Volume or disk filling up: from the way a volume or disk grew over the last two weeks, the monitor works out when it will be full (Storage tab, Filling up). The rule opens a problem when the volume is at least 80% full and that is within 14 days (change the days in the rule). An emptier volume that grows fast is shown on the Storage tab but is not a problem.
  • Certificate expiring: website checks on an https:// address read the site's certificate once an hour (self-signed ones too) and warn 21 days before it runs out.

Maintenance windows

Planned work, such as a firmware update or a reboot. For the time you set, the devices covered still show their problems, but no messages are sent (no reminders and no "back online" either). Failed checks count as planned downtime: they appear in blue on the availability bar and do not lower the uptime figures.

  • One device, now: Maintenance on its page, pick how long. The page says it is in maintenance until when; End maintenance stops it early.
  • A group, a tag or everything, now or later: Settings, Maintenance windows. A window can start at a set time and last up to 14 days. Ended windows stay listed for a week.

A window on a device does not cover the devices behind it on the map; use a group or tag for those or rely on one alert for one failure.

Inventory and new devices

The Inventory page lists every hardware (MAC) address seen on your network, from the switches' address tables and the gateway's address list (and UniFi, when it is connected): its IP address, the switch port or access point it is on, its maker and name where known and when it was first and last seen. Devices you monitor are marked and linked.

  • Edit gives an address your own name, a location, a note and a purchase date. These never change by themselves.
  • New devices: for the first day after the inventory starts it only learns what is there. After that, an address never seen before is announced: an event, the bell and a Telegram message (New device on the network, switched under Notifications, Messages). It stays marked new until you tick Known or press Mark all new as known.
  • Private addresses: phones and laptops often use a made-up address per network, marked private. Some change it every few weeks, which shows up as a new device.
  • Known on a row ends the new mark at once, whether or not the device is online. Add a device puts in an address you know (from its label, say) as known, before it is ever seen.
  • Wi-Fi network: for a device on Wi-Fi (from UniFi), the column shows the SSID it last joined. It is cleared when the device moves to a cable and kept while it is offline.
  • Quiet networks (a tenant's or a guest network): devices on them are still recorded and kept up to date, but never announced, never counted as new (on this page, in the daily summary or /changes) and not touched by Mark all new as known. They are hidden from the list; choose Quiet only or Everything, quiet too to see them. One device can also be made quiet on its own: Quiet in its Edit window.
  • Weak Wi-Fi signal (Edit, for a Wi-Fi device): an access point's Wi-Fi devices on weak signal problem lists every device below the line. For one that is always weak, choose Never report it or Report it only below a line of its own (for example -86 dBm). The Wi-Fi page marks such devices.
  • Forget removes an address; if it shows up again it is new again.

Users limited to some devices do not see the Inventory: it lists the whole network.

Shutting a machine down

When a machine shuts down, its SNMP agent (or a checked service) usually stops a few seconds before it stops answering ping. The warning for that (SNMP agent not responding, not answering) therefore waits one ping interval plus 30 seconds before it goes to Telegram. If the device is offline by then, only the offline message is sent; neither the warning nor its resolved message is (the event log says so). If the device still answers ping, the warning is sent as usual, a little later.

A machine that runs others (a Proxmox host with its containers): set each guest's uplink to the host (Edit device, Place on the map and details). Then the host's offline message lists the guests, instead of one message each. Grouped messages (Notifications, When) combine whatever else arrives together.

A problem on a device that is already offline is not sent: the offline message covers it. So a Proxmox guest that stops because you shut its host down sends no second message. Back online and resolved messages never ring in the silent window (see Notifications).

To restart machines on purpose without any messages, use a maintenance window or the workflow step Suppress notifications. Restarting a machine from Host actions mutes it until it is back.

Host actions (Linux)

A fixed list of maintenance jobs for Linux hosts (Debian, Ubuntu, Proxmox VE), run once over SSH. Open it with Host actions on a host's page, with Fix... next to one of its problems (the actions that suit that problem come first) or from the Automation page. It needs a stored credential (root or a user allowed to run sudo without a password) and the host's SSH key approved, the same as workflows.

  • Checks change nothing and run at one click: what is using the disk (with the big files written in the last day, which is what makes a disk grow), a quick health check, the busiest processes, failed services, one service's status and log, updates waiting, disk health (SMART), read-only filesystems, Docker containers, network and DNS, a security report, time sync, Proxmox storage and ZFS, Pi-hole.
  • Clean-ups and repairs show a preview of what they would change; Run unlocks after it: empty the package cache, shrink the journal, remove unused packages and old kernels, Docker dangling images and build cache, rotate logs, week-old files in /tmp, finish interrupted installs, install updates (no restart), clear failed service markers, flush the DNS cache, update Pi-hole blocklists, start a ZFS scrub.
  • Restarts preview too, then ask you to type the host's name: one service, one Docker container, the services still running old libraries after updates or the whole machine. Restarting the machine mutes its notifications and waits until it stops and answers ping again. It is refused for the machine the monitor itself runs on. The network, systemd and the monitor's own service are never offered for a restart.

When the host is a Proxmox guest the monitor knows and the Proxmox action token is set (Settings, Proxmox), clean-ups and restarts offer Take a Proxmox snapshot first. Nothing in the list deletes files by name or stops guests. Disks, users and the firewall are not touched either; those stay with you or in a workflow you write.

Make this a workflow saves the action as a workflow on that host, ready to run again or to get a schedule on its trigger. The same jobs are in the workflow builder's command templates (on the Run command step) (names start with Host action:). Every run, with its output, who ran it and the problem it was for, is listed under Host actions on the Automation page; the audit log records each run and the host's events record each change.

Pi-hole

Settings, Pi-hole: queries, blocking and blocklists from Pi-hole's own web API (no SNMP needed) plus a real DNS lookup through the Pi-hole every minute. The figures appear on the Pi-hole's device page (add it first, Ping is enough) on a DNS tab: where queries go, the most blocked domains and graphs.

  • Pi-hole 6: in its web interface, Settings, Web interface / API, switch to Expert, Configure app password; copy it and enable it. Pi-hole 5: Settings, API / Web interface, Show API token.
  • Enter the address (http:// and its IP) and the password or token, Test connection, Save. If the address starts with http://, the app password travels unencrypted on your network. Settings shows a reminder.

Alert rules (group DNS): DNS not answering, DNS slow, Pi-hole blocking switched off, Pi-hole blocklists out of date.

Once connected, Pi-hole has its own page in the menu: today's figures, where queries go, the most blocked domains and graphs. When a site breaks because of a blocklist, Pause blocking for 5, 30 or 60 minutes; it comes back on by itself and a pause raises no alert (blocking switched off with no end is still a problem). Resume blocking ends a pause early. Pausing needs an app password that may change settings.

UniFi Wi-Fi

The monitor is built with UniFi networks in mind. Its access points report totals per radio over SNMP; Settings, UniFi adds what each Wi-Fi device experiences, read from the UniFi Network application on your gateway: signal, band, channel, speed, retries, how often it roamed and UniFi's experience score. They are listed on each access point's Wireless tab, weakest first. They also give the Inventory names and makers.

  1. In UniFi, Settings, Admins & Users, Create New Admin: tick Restrict to local access only (no UI.com account and no two-step login), role View Only.
  2. In the monitor: the gateway's https:// address, that username and password; Fetch fingerprint, compare it with the one your browser shows for the UniFi page, Test connection, Save.

Alert rule Wi-Fi devices on weak signal opens a problem on an access point when devices stay below the line (-75 dBm by default) for 15 minutes. As a guide: -67 dBm or better is good for calls, below -80 barely works.

The Wi-Fi page

Once connected, Wi-Fi has its own page in the menu: every access point side by side (devices, weak ones, average experience, bands; click one to show only its devices) and every Wi-Fi device in one list, weakest first, filterable by access point, band and weak signal.

Reconnect

A device can stay on a far access point after you move around the house. Reconnect on the Wi-Fi page drops it so it joins again, ideally to the nearest access point (the device decides). The workflow step Reconnect weak Wi-Fi does it for every device below the weak-signal line on one access point; pair it with the trigger A problem opens, rule Wi-Fi devices on weak signal. A device is reconnected at most once an hour. The Never reconnect list in Settings, UniFi keeps printers and gadgets out of it. Reconnecting needs a UniFi account that may make changes; with a View Only account everything else still works. UniFi's own Minimum RSSI and BSS Transition settings help devices move by themselves.

On the map

With UniFi connected the map uses UniFi's own layout: which device and port each switch and access point is plugged into, plus the switch port of each wired device. Monitored devices on Wi-Fi hang off their access point on a dashed blue line. Each access point counts its other Wi-Fi devices. An uplink set in Edit device still has the last word. A link to one of your own objects (an unmanaged switch) is kept.

Notifications (Telegram)

Settings, Notifications. Messages reach your phone through a Telegram bot you create with @BotFather; the token is stored encrypted. This is the monitor's only connection to the internet.

  • Delivery: the bot, your chat (press Find my chat, send your bot a message within two minutes, press it again and confirm the chat name it shows), a test message and which problems are sent (from a minimum severity or per rule). Send silent test sends one message without a sound and shows the monitor's clock, so you can check both.
  • When: Quiet hours hold non-critical messages and send one summary when they end. The Silent window delivers at once without a sound. Problems from the severity in Still ring from still ring; device offline is critical, so with the default (critical) it rings. Back online and resolved messages never ring. Also here: Repeat reminders for problems nobody has acknowledged, quiet for devices just added (30 minutes by default) and an optional Summary message. The summary comes daily or weekly at a time you choose, with availability, problems, new devices, volumes filling up and certificates running out.
  • Group messages that come at once (under When, on by default): when several devices go down or come back together, as when you restart access points, you get one message listing them instead of one each. Problem and device messages wait until none has come for Wait to group seconds (30), so machines shut down one after another end up together (at most four times that after the first). Fewer than Group from (3) still go one by one. Devices unreachable behind an offline one are listed after it in brackets and counted, for example Offline (6): switch-01 (+ nas-01, web-app), media-server (+ downloads), test. Proxmox messages get their own section. A problem on a device that is already offline (a Proxmox guest stopped, say) is not sent at all: the offline message covers it. The grouped message has its own text under Messages, Several at once, grouped.
  • Messages: the text of each message, with placeholders such as {device} and {problem}.
  • Security alerts (on by default): security alerts tell you about changes to users, credentials and host keys, lockouts, updates and restores, and when HTTPS cannot start. Each names who did it and from which address. They go out straight away, also in quiet hours. The event log only notes that one was sent; the audit log has the details.

Messages that cannot be sent (no internet for a while) wait and are retried for 24 hours. Every message sent shows on the device's events.

Asking the bot: send it a command from your chat and it answers. All of them only read; none changes anything.

  • /status: how many devices are up and down, which are down, the open problems and any maintenance on now.
  • /problems: the open problems, most severe first, with how long each has been open.
  • /device nas-01: one device by its name, the start of its name or its address: state, ping, CPU, memory, uptime and its open problems.
  • /changes: the last 24 hours: new devices on the network, restarts, problems opened and resolved.
  • /help: the list.

Only your chat (the one in Delivery) gets answers; anyone else who finds the bot is ignored and noted in the audit log. Every command answered is in the audit log too. The monitor fetches new messages from Telegram itself, so nothing connects in from the internet. Switch it off with Answer commands under Delivery.

The command builder (the Commands tab) lists every command, built in and your own. Each has an on box; Telegram's command menu (type / in the chat) shows exactly the ones that are on.

  • Built-in replies: Edit opens the reply text with its placeholders ({up}, {down_list}, {figures} and so on). One problem in a list sets how each problem is written in /problems and /device. Original puts the first text back.
  • Add command: a name (lowercase, like wifi), a description for /help and the menu. Then what it Shows: devices, problems, Wi-Fi networks, access points or Wi-Fi devices, Proxmox VMs and containers, nodes or storage, Pi-hole or storage forecasts.
  • Covers: tick the items it is about (devices one by one, a tag or a group; SSIDs; guests); nothing ticked means all. Only narrows it further: only down, only running, only weak signal, only full within 60 days.
  • The reply: a header (once), a line (once for each item) and a footer (once). The right side lists the placeholders for each; for devices also any figure a device records, as {metric:name}, your custom SNMP values included.
  • Preview: the real reply from your data now, as you type. The box under it tries a word after the command: /wifi guest lists only items with "guest" in their name.

Sort by orders the lines by one of the line's placeholders (numbers by value; tick highest first to turn it round). At most keeps only the first so many; {more} says how many it left out.

A placeholder with nothing to say is empty. A line left empty is dropped, so {down_list} adds nothing while everything is up. A misspelled placeholder stays as written, so you see it. Commands only read: they cannot run anything or reach anything the monitor does not already watch.

Writing messages: tricks that work everywhere

Every Telegram text (notification messages, the workflow step, the built-in replies and your own commands) understands the same extras. The editors list them under Tricks; click one to insert it.

  • Conditions: {if down > 0} ... {elif problems} ... {else} ... {end}. Compare with > < >= <= == !=, combine with and, or, not; text goes in quotes: {if state == "down"}. A name on its own is true when it is not empty and not 0. A line holding only {if}, {else} or {end} leaves no empty line.
  • Arithmetic: {= up / total * 100 | round:1} with + - * / %, brackets and min(), max(), round(x, n), abs(), floor(), ceil(). A name with a dash or colon goes in square brackets: {= [metric:temp.cpu-0] * 1.8 + 32}.
  • Numbers: a value such as 34%, 12 ms or -80 dBm counts as its number in arithmetic, comparisons and number filters.
  • Filters, after a bar and applied left to right ({cpu|round:0|default:"-"}): upper lower title trim; default:TEXT (when empty); before:TEXT and after:TEXT (added only when there is a value); round:N fixed:N int abs add:N sub:N mul:N div:N; plural:device ("3 devices"; plural:box:boxes for odd words); bar:10 (a 0 to 100 value as ▰▰▰▱▱); truncate:N pad:N lpad:N replace:OLD:NEW; for lists, one item per line: first:N last:N sort rsort unique count join:", ".
  • A literal brace is written {{ or }}. A mistake in a tag shows as {?what went wrong} in the preview, so it is caught before it is sent. A template that makes its text far too long stops there: the preview tells you, and a saved message sends a short notice instead.

Automation

The Automation page has four parts: Credentials, Workflows, Host actions and Workflow runs.

  • Credentials: SSH logins (password or private key) stored encrypted. A key can be pasted or generated here. Test tries one on a host.
  • Host keys: before the monitor connects to a host over SSH you approve its key once, in a window that opens when it is needed. A changed key stops the connection until you approve the new one.
  • Workflows: steps run one after another: commands on one or more hosts, pauses and waits until a host stops or starts answering ping or SNMP. A step can go to another step when it fails. Use them for update and restart sequences where one thing must be back before the next goes down.
  • Workflows run by hand, on a schedule or when something happens: a device goes offline or comes back, it answers ping but not SNMP, a measurement crosses a value, a watched service stops or a problem opens. Each run is kept with the output of every step, under Workflow runs.
  • Host actions: pick a host to open its Host actions, the fixed maintenance jobs for Linux hosts. Every run is listed here with its output; click one to see it again.

The workflow builder

The left column has two tabs, Steps and Templates. The middle is the canvas. The right side shows whatever you picked: a step's settings, the trigger or a template's options.

Steps come in three families. Each family has its own colour, the same in the list and on the canvas:

  • Do something: Run command (an SSH command on one or more hosts; host actions are among its command templates, named Host action:), Snapshot a Proxmox guest and Reconnect weak Wi-Fi.
  • Wait: Wait (a number of seconds), Wait until down, Wait until up (ping) and Wait for SNMP.
  • Tell and keep quiet: Send Telegram, Suppress notifications and Notifications back on.

Picking a template on the left shows on the right what it does, the hosts to tick (those it suits are marked) and its options: the credential, whether to suppress notifications and whether to send a quiet summary at the end. Add these steps puts them on the canvas after the selected step, where you can change them like any other step.

Restarting without a flood of messages

  • Suppress notifications (a step): keeps Telegram quiet for this workflow's hosts, devices you pick, a group, a tag or everything. It opens a maintenance window, so problems still show and are logged and the downtime counts as planned. Until the run ends lifts it when the run finishes (however it finishes) plus a few minutes, so the "back online" messages stay quiet too; At most is a safety limit.
  • Notifications back on (a step): ends the suppression early, for example before a final check you do want to hear about.
  • Send quietly (on Send Telegram): the message arrives without a sound. Its text understands the message tricks, so {if status == "a step failed"}❌{else}✅{end} works.

Ready-made workflows

The Templates tab in the workflow builder adds whole sequences; the ones that restart things suppress notifications by default and can end with a quiet summary.

  • Update and restart Linux hosts, Update Linux hosts, no restart, Restart UniFi devices in order (furthest from the gateway first) and Restart sequence (any hosts, your command).
  • Snapshot, update and restart Proxmox guests: a snapshot first for every host that is a Proxmox VM or container.
  • Restart a service on Linux hosts: restarts it and checks it is running; pair it with the trigger A watched service or process stops.
  • Free disk space on Linux hosts and Health check, results on Telegram (changes nothing; good weekly).
  • Update Pi-hole and its block lists and Reconnect weak Wi-Fi on access points.

These are made of host actions, the same fixed jobs as the Host actions window:

  • Weekly tidy-up on Linux hosts: empties the package cache, shrinks the journal, removes unused packages and old kernels, clears week-old files in /tmp. Give it a weekly schedule.
  • Disk filling up: report, clean, report again: what is using the disk, the safe clean-ups, then the disk again so the summary shows what was freed. Pair it with the trigger A measurement goes above or below a value on disk use.
  • Security and updates report: changes nothing. The security report, updates waiting and failed services.
  • Install updates, then restart what still uses old libraries: the machine itself keeps running.
  • Docker tidy-up: lists the containers, then removes untagged images and build cache only.
  • Disk health check: changes nothing. SMART health of every disk, filesystems that went read-only and time sync.
  • Proxmox host check: changes nothing. Storage and ZFS pools, failed services and updates waiting.
  • Clear failed services and check again: lists failed services, clears their failed markers and lists them again, so only the ones that are really broken remain.

Proxmox

Settings, Proxmox: switch it on, then connect with a read-only API token. Once a connection is saved, Proxmox has its own page in the menu: nodes, VMs and containers, storage, backups and failed tasks. Click a node or guest for CPU, memory, network and disk graphs from Proxmox's own history.

  1. In Proxmox: Datacenter, Permissions, API Tokens, Add. User root@pam, Token ID monitor, keep Privilege Separation ticked. Copy the secret: it is shown once.
  2. Give the token read access: click Permissions itself in the left menu (not API Tokens or Roles under it), Add, API Token Permission: path /, the token, role PVEAuditor, Propagate ticked. Or in the host's shell: pveum acl modify / --tokens 'root@pam!monitor' --roles PVEAuditor
  3. In the monitor: the address (https://, the host, port 8006), the token ID and the secret. Fetch fingerprint, compare it with the node's certificate in Proxmox, then save. Test connection says what the token can see or which permission is missing.

What it adds elsewhere

  • The map: every monitored VM and container hangs off the node Proxmox runs it on. A guest is matched to a monitored device by its name, a container's address or its network card's address seen by the gateway, so the names need not match (a guest called Win11 can be the device desktop-01).
  • Alerts (Alert rules, group Proxmox): a guest set to start at boot that is not running (it clears within a minute of the guest running again); one that restarted several times in an hour; a guest's memory or a container's disk nearly full. They show on the guest when it is monitored, otherwise on its node.
  • Forecasts: each storage pool (local-lvm, your data pools) is recorded every five minutes on the node's device. Its Storage tab says when it will be full.
  • Monitor: a guest that is not monitored yet has a Monitor button on the Proxmox page, which opens the Add window with its name and address.

Actions (optional)

The token above only reads. A second token lets the Proxmox page Start, Shut down (cleanly, through the guest) and Reboot guests. It also gives the workflow step Snapshot a Proxmox guest: take a snapshot before an update, so a failed update can be rolled back in Proxmox (the guest, Snapshots). Settings, Proxmox, Actions has the three commands to make it: a role with only VM.Audit, VM.PowerMgmt and VM.Snapshot, a token and that role on /vms. Every action asks for your password, is confirmed and is in the audit log.

Network map

How your devices connect, drawn from what the switches report (and the uplinks you set in Edit device). Drag to arrange, click a device to see what depends on it, add objects the monitor cannot see (an ISP modem, a wall socket) and link them by hand.

  • Reading it: the coloured edge of a box is its state (the key at the bottom left). Solid lines are cables, dotted lines are virtual machines and services on a host, blue lines are links you drew. The small tags on a line are the switch ports at each end. Hover a line to pick it out.
  • Moving around: drag the background to pan, scroll or use + and − to zoom, Fit to see everything. A box you drop snaps to the grid and its branch moves with it; hold Alt to move one box on its own. Edit, Arrange as tree tidies everything.
  • This monitor is not drawn. With nothing selected, the side panel says where it connects; clicking a device it depends on warns you that restarting that device cuts the monitor off.

Events and the audit log

  • Events: everything that happened to devices: problems and recoveries, ports going up or down, restarts, software changes, messages sent, actions run. Search, filter by device, tag, severity, type and time.
  • Audit log: who did what in the app: logins, settings changed, devices added, credentials used. Search and filter by category and time. Details of sensitive entries are only shown to users allowed to see them. It also shows who did it and from which address. It is kept for at least 90 days. Events have their own retention in Settings, Data retention and storage.
  • The bell at the top right collects what needs your attention.

Users and security

  • Logging in: when you are signed out, the login screen fills the whole page. A refresh never shows the app behind it. Sessions end after a while without use; repeated wrong passwords lock the login for a time. After you log in you return to the page you were on.
  • Users (Settings, Users): one account per person. Roles give sets of permissions (Viewer: read only; Operator: day-to-day running; Administrator: everything) or Custom picks them one by one; a user can be limited to some templates or devices. A user limited this way can only act on those devices: acknowledging, maintenance windows, workflows and Proxmox guests mapped to them. The map, dashboards, groups and tags are shared by everyone, so changing them needs access to every device, as do Pi-hole blocking, Wi-Fi reconnect and the Inventory.
  • Two-factor authentication (Settings, Account): an authenticator app code at login, with one-time recovery codes. Recommended for every administrator. An administrator can require it for administrators or for everyone in Settings, Login security. It is off until you choose. Anyone it covers sets it up straight after their next password.
  • Confirmations: changes that lose data or touch devices ask for your password again; anything that grants access or holds secrets also asks for the authenticator code. The confirmation lasts a few minutes.
  • Secrets (credentials, tokens, communities) are encrypted with the vault key; they are never sent to the browser or written to logs.
  • Text from your devices: text and numbers from your devices are always shown as plain text, so a device cannot add its own content to a page.
  • Managing users without being an administrator: someone with Manage users can add and change users with up to their own permissions and device access. Someone limited to some devices can only change users whose device access is inside their own. Only an administrator can make an administrator, give Manage users, change an administrator account or change their own rights.
  • Stored passwords stay where they belong: Test connection for Pi-hole, UniFi and Proxmox reuses the saved password or token only for the saved address and certificate; for a new one, type it again. Testing asks for your password first, like saving.
  • Workflows: saving one asks for your password and may only use devices you can see. Run logs need Run or Edit workflows and show only your devices. A scheduled or event workflow is skipped (with a note in its run) when the person who last saved it is blocked, deleted or lost the rights.
  • Stored credentials: Use stored credentials lets someone run commands on hosts as a credential's user, often root, on every device they can reach: in workflows, host actions, Fix SNMP and credential tests. A password credential also needs Manage credentials. Operators have Use stored credentials so they can run host actions, but they cannot run a workflow that logs in with a password. A host action or workflow step shows which user it runs as.
  • Devices: changing a device's address forgets its approved SSH host key, so the next SSH connection asks you to approve the new one. Approving a host key needs Manage credentials, because it decides where stored credentials are sent. Forgetting one needs only Manage devices.
  • 2FA: turning it on or off logs out your other sessions. Each code works once, even when sent twice at the same moment. Wrong authenticator codes count like wrong passwords. After a few wrong tries the wait before the next one gets longer, even if you enter your password again. A successful login clears it.
  • Web checks report a redirect instead of following it, and do not fetch the monitor's own addresses (127.0.0.1, localhost and link-local).
  • The container: only SSH and the web page can be reached from outside, and only from private addresses, or from the ones set in ADMIN_NET at the top of home_monitor.sh (for example "192.168.1.0/24"). Syncthing and DHCP are let in from the LAN; everything else coming in is dropped, and new SSH connections are limited to 10 a minute per address. Set ROOT_SSH_KEY to your public key (the line itself, or a file on the Proxmox host such as /root/.ssh/id_ed25519.pub) and root logs in over SSH with that key only; the Proxmox console still takes the password. On an upgrade a blank setting keeps what the box already uses, and a different value is shown so you can choose. Run without a person at the terminal, the box keeps its own. Both are checked strictly as IPv4 or IPv6 addresses or networks, and IPv6 entries in SNMP_ALLOW are allowed in on IPv6 (an existing box answers SNMP on IPv6 only after a rebuild). The installer tests the firewall rules before turning them on; if they cannot be turned on, the last screen says the inbound firewall is NOT active and how to fix it.
  • Unprivileged container: UNPRIVILEGED=1 at the top of home_monitor.sh makes the safer kind, where root inside the container is not root on the Proxmox host. It cannot mount NFS itself: the Proxmox host copies the Syncthing identity in (and, for a rebuild with RESTORE="latest" from BACKUP_NFS, the newest backup). Other shares are passed in from the host as mount points, for example pct set 201 -mp0 /mnt/pve/media,mp=/mnt/media. An existing container changes kind only by a rebuild: set it, then bash home_monitor.sh --rebuild with RESTORE="latest". The installer now asks for this on a new install or a rebuild.
  • Shares (NFS mounts and the Syncthing folder) go below /mnt or /srv, and are always mounted with nosuid,nodev,noexec: nothing on a share can run as a program in the container. The container checks this again before it mounts anything, whatever the database or a backup says.
  • Forgot the password? With 2FA and Telegram set up, press Forgot your password? on the login page: it asks for your authenticator code and sends a one-time code to Telegram. Otherwise, on the container (or the --local machine): /root/reset-admin.sh (it can also turn 2FA off for that user, and stop requiring 2FA if you have no phone to set it up with).

HTTPS

Settings, HTTPS decides how browsers connect. The address stays the same (same port); old http:// links and bookmarks are sent on to https://.

  • Certificate made here (a new install starts with this): the monitor makes a certificate for its own name and address and renews it before it runs out. Browsers warn once because no public authority signed it. Check that the fingerprint in the warning matches the one in Settings, HTTPS and continue. Or press Download certificate and add it to your computer's or phone's trusted certificates to stop the warning. Opening the monitor by another name (for example monitor.home.example.com)? Add it under Extra names.
  • Your own certificate: from your own certificate authority or anywhere else, for the name you use. Paste or choose the certificate (server certificate first, then intermediates) and its key without a passphrase; it is checked before it is used. You get a warning in the bell and on Telegram from 21 days before it expires.
  • HTTP: not encrypted. Only for a network you fully trust.

The certificate and its key are kept in the database (the key encrypted), so a normal backup carries them and a restore brings them back. After an upgrade from a version without HTTPS the monitor keeps plain HTTP and asks an administrator once which to use.

Locked out by a certificate? In the container shell run /root/update.sh and choose 6: the monitor answers on plain HTTP again and the certificate is kept.

If HTTPS ever fails to start, the monitor keeps working and tells you, but it will not accept logins from other computers over plain HTTP. Option 6 is the way back in. To avoid sending your password unprotected, open an SSH tunnel with ssh -L 8080:127.0.0.1:8080 root@<address> (use your monitor's port) and open http://127.0.0.1:8080 instead.

Uptime Kuma or another tool checking the monitor over http:// is redirected once HTTPS is on: point it at https:// and allow the certificate (in Uptime Kuma, "Ignore TLS/SSL errors" for one made here).

Backups, restore and upgrades

Backups

A backup is made every day by itself. Back up now (Settings, Backups) makes one at once. Each backup records the version that made it. Without Syncthing they stay in the container (the newest 7); with Syncthing they are written to the synced folder, so your NAS holds them. A backup has everything a rebuild needs. The key that unlocks the stored passwords goes with it sealed with your backup passphrase; without a passphrase it stays only in backups kept inside the container.

The backup passphrase

Set one as soon as you can. The easiest way is Settings, Backups, Set backup passphrase: confirm your password (and your code, with 2FA), type a passphrase of 12 characters or more twice and keep it in your password manager, apart from the backups. The container saves it and makes a sealed backup straight away. Telegram sends a security alert and the audit log records who did it. The same button changes it later; backups made before a change still need the old passphrase. You can also do it in a root shell in the container with /root/backup-passphrase.sh (or /root/update.sh, option 7). On a new install you can also set BACKUP_PASSPHRASE at the top of home_monitor.sh.

With a passphrase, every backup carries a check that proves it was not changed, and the key inside it is sealed: someone who copies the backup share gets nothing they can open. Without one, Settings, Backups shows a warning with the command. Backups that leave the box (Syncthing or a share) then go without the key, so a rebuild from them cannot use the stored passwords, and no backup can be proven unchanged.

Backups you already have stay as they are until the daily clean-up removes them, with the newest 7 kept. Copies on your NAS or in Syncthing's history may still hold the key in the clear, so remove them there if you want them gone now. Changed the passphrase? A restore of an older backup asks for the passphrase it was made with.

The copies the box makes for itself before an update, an upgrade, a restore or an undo are kept in /var/lib/homelab-monitor-safe, which only root can read. They always carry the key, so Undo works whatever the passphrase is.

Updating from the app

Settings, Updates (administrators) shows the version running now. The monitor looks for a new version once a day by itself (Check for updates every day, on unless you turn it off), and Check for updates looks straight away. When a new version is out, a red 1 appears on Settings in the menu and on Updates in the settings menu.

The Updates card then shows the new version with what is new in it, and in every version between yours and the newest, so nothing is missed when you skip a few. Read it, then choose:

  • Update now asks for your password and authenticator code, then the box does the rest. A progress screen shows each step as it happens: download, the signature check, a trial on a copy of your data, the backup, installing and starting the new version. The monitor restarts near the end; the page waits and reconnects by itself, usually within a minute or two. It ends with Updated and a button to reload the page, or with what went wrong and the previous version running again.
  • Skip this version takes the red number away. The version stays in the card (with Show it again and Update), and the number comes back when a newer one is released.

Cut short? If the machine restarts or loses power during an update, the monitor sorts it out when it starts again: the app is put back in one piece, the update is listed in the history as cut short (with whatever it logged) and Update works again. When the new version was already in place but not yet checked, Undo is offered for two days to put the previous version and its data back.

Update history, under the card, lists every update, upgrade and undo with its date, the versions and whether it passed or failed. View log opens the full log of that run in the page, with Copy and Save as a file, so there is no need to read it on the box. Upgrades run with bash home_monitor.sh --upgrade from the Proxmox host are listed too. Passwords and tokens in a log are masked, and the newest 25 runs are kept.

  • Only signed releases. A release is installed only when its signature matches the key built into your copy, and only when it is newer than what runs now.
  • Your settings stay. The port, who may reach the monitor and the other choices made when it was installed are kept on the box and used by every update. An upgrade from the Proxmox host keeps them too.
  • Only root goes online. The outbound firewall lets root on the box reach GitHub for this; the monitor itself still cannot reach the internet.
  • Undo for two days. Each update keeps its own backup and the previous version for two days. Two ways back are offered in the same card:
    • Back to the previous version, keep today's data. Everything since the update stays; features new in the update are gone until you update again. This is only offered when the update did not change how the data is stored.
    • Back to the previous version with the data from before the update. Anything changed since the update (history, devices, settings) is lost.
    Either way the state at that moment is backed up first (in root's own folder, under pre-rollback). Undo uses only the copy the box recorded when it made it, and checks that copy is unchanged before anything stops.
  • First time: an install made before 0.9.0 needs one bash home_monitor.sh --upgrade from the Proxmox host, which records its settings on the box. From then on Update works from the app.

Upgrading

On the Proxmox host: bash home_monitor.sh --upgrade (on a --local install: sudo bash home_monitor.sh --local --upgrade). The container is the one with the Proxmox tag homelab-monitor; with several tagged it asks which. Only Proxmox's own container settings are read to find it, nothing inside other guests. Without a tagged container it stops and shows how to add the tag (a container made by an older home_monitor.sh needs it once):

ID=201; T=$(pct config $ID | awk '/^tags:/ {print $2}'); pct set $ID --tags "homelab-monitor${T:+;$T}"

Use your container's ID (pct list shows them). An upgrade changes only the monitor inside the container: its CPU, memory, disk, network and start at boot stay as they are. It shows the same progress screen as an install (each step, a bar and the time) and ends on a summary of what its check found. The steps:

  1. Checks the container and your data with the new version first (it tries the update on a copy of your database). If something blocks it, it stops with nothing changed and says how to rebuild instead.
  2. Installs anything the check found missing (a package, a folder).
  3. Backs up.
  4. Replaces the app (data, settings and passwords stay).
  5. Waits for the new version to answer. If it does not, it puts the old version and data back by itself.

bash home_monitor.sh --check runs only the check, if you want to look without upgrading.

Settings, System shows the version now running. A new middle number (0.3 to 0.4) brings new features and may update the database; a new last number (0.3.0 to 0.3.1) brings fixes. Your next login after an upgrade lists what changed.

Restoring a backup into the same container

When the monitor misbehaves and you want to start again from a backup without a new container: Restore a backup in the menu, or bash home_monitor.sh --restore (sudo bash home_monitor.sh --local --restore on a VM). It finds the container by its tag and lists every backup the container can see: its own backup folder (daily ones and those made before an upgrade or restore), the Syncthing folder, any mounted share and /root. Each line shows when it was made, the version that made it and its size, newest first. Pick one by its number, then type RESTORE. It then:

  1. Checks the backup with the new version first; one it cannot restore is refused with nothing changed.
  2. Keeps a copy of what is there now (in root's own folder, /var/lib/homelab-monitor-safe, under pre-restore). The newest 3 are kept, and older ones go after 30 days.
  3. Wipes the app and its data, puts a fresh copy of the app in and restores the backup.
  4. Waits for the monitor to answer. If any of this fails, the copy from step 2 is put back.

Before you type RESTORE it shows the site settings in the backup (shares and Syncthing) that will be applied afterwards; any that break the rules above are marked Refused, not applied. A backup made with a passphrase other than the one on the box asks for it. A backup that cannot be proven unchanged (an older one, one made without a passphrase or one changed since) shows the accounts in it and how many stored credentials it holds, and goes ahead only when you type UNVERIFIED. A backup without its key, on a box that does not have that key either, can only come back without its stored passwords, SSH keys, tokens and 2FA: type FORGET and enter them again afterwards. Only backups with plain file names (letters, digits, dot, dash and underscore) are listed.

The container itself (CPU, memory, disk, network) is not changed. With no backup in any of those places it stops and says so: copy one into the container first, for example from the Proxmox host with pct push 201 monitor-backup-<date>.tar.gz /var/lib/homelab-monitor/backups/monitor-backup-<date>.tar.gz, or mount the share that holds them. Log in afterwards with the accounts from the backup.

Rebuilding and restoring

For a container that cannot be upgraded in place or a new host: set RESTORE="latest" and the backup source at the top of home_monitor.sh, then bash home_monitor.sh --rebuild. A rebuild finds the container by its tag too and makes the new one with the old one's ID, name, CPU, memory, disk and network card (address and MAC). Or restore by hand in the container with /root/restore.sh. A restore checks the backup first: one from a newer version or a damaged one is refused and your current data stays. With RESTORE="latest" a backup that cannot be proven unchanged is refused; set RESTORE_UNVERIFIED="yes" for that one run to restore an older backup on purpose, or use /root/restore.sh at a terminal, which shows it and asks. An older backup is brought up to date; anything in it the new version no longer uses is kept, not deleted.

Troubleshooting

Reporting a problem

Something not working as it should? Settings, System, Report a problem (administrators) makes a short report: the version, how the monitor was installed, the system, device counts by template and status, a few settings that are on or off, storage and backups, recent updates and the warnings the monitor logged since it started. Addresses, device and user names, email and web addresses and anything that looks like a password are masked, and stored passwords are never read. You see it all first: Copy or Save as a file, then Open a new issue on GitHub and paste it below what happened. The monitor sends nothing by itself.

When the web page will not open, run ./home_monitor.sh --report on the Proxmox host (sudo ./home_monitor.sh --local --report on a machine of its own), or choose it in the menu. It changes nothing, adds whether the service is running and the end of its log, prints the report and saves it as home-monitor-report-<date>.txt beside the file.

env: 'bash\r': No such file or directory when running home_monitor.sh
The file was saved with Windows line endings (an editor or a text-mode copy). Run it as bash home_monitor.sh ...: it fixes itself and carries on. Or once: sed -i 's/\r$//' home_monitor.sh.
Proxmox connects but shows almost nothing
The token has no permission of its own. Add the API Token Permission (see Proxmox); Test connection names what is missing.
"SNMP agent not responding (host answers ping)"
The community is wrong, SNMP is off or a firewall blocks UDP 161. If the device has no SNMP at all, set its template to Ping only in Edit device.
"SNMP agent only exposes basic system information"
The host's snmpd allows only the system group. On Linux hosts use Fix SNMP.
Fix SNMP: "could not log in over SSH"
Check the credential. Debian and Ubuntu refuse root password logins by default. Copy console commands (beside Preview changes) gives one line to paste on the host that lets the monitor in; or use an SSH key credential or a user with passwordless sudo. With an SSH key credential the commands install the key and turn password logins from the monitor off. With a password credential they turn on password login, including for root, from the monitor's address only.
Fix SNMP: "snmpd did not start"
The message includes snmpd's own log lines; the previous file was put back. Fix what they name or use Copy as commands.
"The monitor is busy. Please try again in a moment."
If the page says the monitor is busy, too many connections are open at once. It clears by itself within seconds.
A device page or graph looks out of date after an upgrade
Reload the page with Ctrl+F5 so the browser fetches the new files.
